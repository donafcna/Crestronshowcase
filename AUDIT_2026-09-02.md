| `pressDigital`, `selectSource`, `changeRoomIphone` | morts |
| `applyLanguage` | mort |

L'envoi de la commande console continue de marcher, lui : `sendConsoleCommand`
est défini dans le `<script>` du `<head>` (ligne 91), bloc distinct et valide.
D'où l'asymétrie observée « ça part, ça ne revient pas ».

`ControlSystem.cs` L779-802 : sur réception du serial 103, `SendControlSystemCommand`

### Détail bug 3 — thème light

`index.html` L500-539, sélecteur `ch5-button[customClass~="room-selector-btn"]` :

```css
508      color: #ffffff !important;      /* blanc en dur, jamais var(--text-primary) */
...
536      color: #ffffff !important;      /* idem sur [selected="true"] */
```

| Thème | Fond sidebar | Texte pièces | Lisible |
|---|---|---|---|
| dark | `rgba(22,25,32,.65)` (L279) | `#ffffff` | oui |
| **light** | `rgba(255,255,255,.85)` (L290) | `#ffffff` | **non** |
| glass | `rgba(255,255,255,.1)` (L300) | `#ffffff` | oui |
| cyber | `rgba(13,17,33,.7)` (L311) | `#ffffff` | oui |

Le sélecteur actif en `rgba(255,255,255,0.08)` (L533) est invisible lui aussi sur
fond blanc.

**Point de fond** : sur ~2900 lignes de CSS, les variables de thème ne sont
consommées qu'à une trentaine d'endroits. Tout le reste est en dur avec
`!important`. Changer de thème ne modifie en pratique que le fond du body,
3 conteneurs et quelques textes. Le bug 3 est le symptôme visible d'un système
de thèmes qui n'est appliqué qu'à 5 % du fichier.

### Détail bug 4 — thème glass iPhone

`iphone.html` L744-746, roue « Réglages » :
`background: rgba(255,255,255,0.05); border: 1px solid rgba(255,255,255,0.1); color: var(--text-primary)`

En thème glass (L201-210) : `--container-bg: rgba(255,255,255,0.1)` et
`--text-primary: #ffffff`. C'est le **seul** thème où le panneau, l'habillage du
bouton et la couleur du glyphe sont blancs simultanément.

S'ajoute `--blur-val: blur(25px)` (contre 15px ailleurs) sur `.header-section`
L262-263. En WKWebView (Crestron Go), `-webkit-backdrop-filter` crée un contexte
d'empilement ; sans couche opaque en dessous (`--bg-color: transparent`, L202),
l'échantillonnage rend une couche quasi blanche au-dessus des enfants statiques.
C'est ce qui rend le symptôme spécifique à l'iPhone — le même CSS glass dans
`index.html` (L297-306) tourne sous Chrome desktop sans problème.

Correctif proposé :

```css
body.theme-glass button[onclick*="openSettingsModal"],
body.theme-glass .popup-trigger-btn {
    background: rgba(0, 0, 0, 0.35) !important;
    border-color: rgba(255, 255, 255, 0.55) !important;
    color: #ffffff !important;
    position: relative;              /* sort le bouton de la couche backdrop iOS */
    z-index: 1;
    text-shadow: 0 1px 3px rgba(0,0,0,.8);
}
```

Remplacer aussi l'emoji `⚙️` par le SVG engrenage déjà présent dans le fichier
(L2550) : `fill` explicite, contraste maîtrisé quel que soit le thème et la police
emoji système.

> À faire **après** la ligne 1478 : en l'état, ce bug est inobservable puisque
> `applyTheme` fait partie du code mort.

### Détail bug 2 — dropdowns XPanel

Deux causes plausibles, à départager sur cible (`index.html` L107-218) :

1. **`WebXPanel.isActive` faux au moment du `DOMContentLoaded`** (L115) → `isXpanel`

   `<input type="date">` natif qui s'affiche. « Le menu déroulant ne fonctionne pas »
   parce qu'il n'apparaît jamais.
2. **Format de date non padé.** Les `<option>` sont générées padées (`"01"`…`"31"`,
   `"01"`…`"12"`, L192-202). Si le CP4 renvoie `3/9/2026` sur le String 104,
   `setDateFields` (L197) fait `daySelect.value = "3"` → aucune option ne matche →

Test à faire : ouvrir la console du navigateur sur l'XPanel et logger

## 5. `deploy.ps1`

Chaîne : version++ → `version.js` + `build_date.json` → `villa_config.json` copié en
`src/` **et** embarqué dans `src/villa_config.js` → `npx ch5-cli archive` →
`pscp` vers la TSW `/display/` + `PROJECTLOAD` → `pscp` vers le CP4 `/user/` et
`/program<slot>/` + `progload`.

Anomalies :

- Le CPZ est pris dans **`bin\Debug`** (L157) : un binaire Debug part en production.
- **Aucune validation JSON** sur le chemin `cp4`/`all` (L150-155), alors que le chemin
  `config` en fait une (L129). Combiné au risque **A**, un JSON malformé peut rendre
  le processeur muet.
- `progreset -p:01` **codé en dur** (L139) alors que `progload` utilise `$S.CP4.Slot`.
- `-Target cp4` ne régénère **pas** `src/villa_config.js` : la copie embarquée dans le
  CH5 peut diverger de `/user/villa_config.json`.
- La version est incrémentée **avant** le build : un `ch5-cli archive` en échec brûle
  un numéro.
- Mots de passe passés en clair via `-pw` sur la ligne de commande `plink`/`pscp` →
  visibles dans la table des processus.
- **Rien n'est déployé pour l'iPad (0x05) ni l'iPhone (0x06)** : le `.ch5z` ne va que
  sur la TSW. Ces clients Crestron Go peuvent tourner sur une version antérieure.

## 6. Cause structurelle : la duplication index/iphone

**42 fonctions sur 46 sont communes** aux deux fichiers, par copier-coller divergent :
`applyTheme`, `applyLanguage`, `generateDynamicUI`, `initVillaConfigLink`,
`sendConsoleCommand`, `refreshIptable`, tous les `open*/close*Modal`… Les
dictionnaires de traduction fr/en/es/de/ru et `fallbackConfig` sont dupliqués
intégralement — **et c'est précisément dans cette copie que se situe la corruption
de la ligne 1478**.

Deux divergences déjà installées, à corriger au passage :

1. Dans `iphone.html`, les fonctions console (`sendConsoleCommand`, `refreshIptable`,
   `openAdminModal`…, L72-118) sont **à l'intérieur** du garde
   `if (typeof WebXPanel !== 'undefined')` (L21). Dans `index.html` elles sont au
   niveau racine (L9141-9168), donc inconditionnelles. Si `js/webxpanel.js` ne se
   charge pas en contexte Crestron Go natif, l'iPhone perd aussi le bouton
   « Envoyer » et l'ouverture du modal admin.
2. `index.html` appelle `refreshIptable()` sur `CONNECT_CIP` (L92) **et** sur
   `DOMContentLoaded` (L100). `iphone.html` ne le fait dans **aucun** des deux
   handlers équivalents (L129-139).

Extraire les ~42 fonctions communes dans un `js/villa-common.js` partagé est la
seule vraie parade à ce type de divergence.
